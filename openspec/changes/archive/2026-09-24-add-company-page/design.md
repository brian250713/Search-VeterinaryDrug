# Design

## Context

- 詳情頁與成分頁已經改成「單一殼頁加分片資料」的架構（見已歸檔的 `client-render-detail-pages`）：`src/lib/shard.ts` 以 FNV-1a 雜湊把 key 分到固定數量的 JSON 分片，建置端 `scripts/build-shards.ts` 與瀏覽器端用同一個函式找分片。
- 成分頁 `src/pages/ingredient/index.astro` 的篩選、單方／複方 → 劑型分組與產品卡片渲染都寫在頁面的 `<script>` 裡，約 250 行；水產物種集合與蛋雞／蛋鴨判斷和 `src/lib/filter-engine.ts` 重複了一份。
- 資料現況（13,737 項產品）：業者名稱 408 種，空白 7 筆；製造廠名稱 346 種，空白 3,707 筆（大多是輸入產品）；兩者合計約 600 家公司。有 4,710 項產品的業者與製造廠相同。以大小寫與全半形括號正規化後沒有重複的業者名稱，但有 3 個製造廠名稱含連續空白，例如 `SWISS PHARMACEUTICAL CO.,  LTD.`。
- 公司名稱多為中文，目前的 slug 規則（英數小寫加連字號）不適用。

## Goals / Non-Goals

**Goals:**
- 公司頁的載入成本與成分頁相當：開啟一個公司頁只下載一個分片。
- 成分頁與公司頁共用同一份篩選、分組與卡片渲染程式，成分頁的畫面與行為不變。

**Non-Goals:**
- 公司總覽頁（類似成分總覽）與公司名稱搜尋。搜尋頁本來就能以業者名稱搜尋，之後有需要再加。
- 合併同集團的不同分廠或名稱變體（例如「第一廠」與總公司）。資料中沒有可靠的集團對照，錯誤合併比不合併的傷害大。
- 搜尋索引與詳情頁產品分片的結構調整。

## Decisions

### D1. 公司識別：正規化後的名稱本身，不另外產生 slug

公司 key 為 `normalizeCompanyName(name)`：去除前後空白，連續空白（含全形空白）合併為一個半形空白；不改大小寫與標點。網址直接用 `?name=<encodeURIComponent(key)>`，瀏覽器端讀到參數後先做同樣的正規化再查表，所以使用者手動輸入或貼上多餘空白的名稱也查得到。

- 替代方案：以名稱雜湊或流水號當 slug。網址較短，但不可讀，而且流水號會在資料更新時漂移，已分享的連結會失效。中文名稱經 URL 編碼後雖然較長，但穩定且能從網址看出是哪家公司。
- 分片雜湊直接對正規化名稱做 `fnv1a32`。這個函式以 UTF-16 code unit 計算，建置端（Node）與瀏覽器端結果一致，中文不需要另外處理。單元測試固定幾個中英文名稱的分片編號，防止漂移。

### D2. 公司分片：64 片，產品摘要加上角色

新增 `COMPANY_SHARDS = 64`，分片路徑 `data/company/NNN.json`，內容為：

```ts
interface CompanyDetailShard {
  [name: string]: {
    company: { name: string; addresses: string[]; vendorCount: number; factoryCount: number };
    products: CompanyProductSummary[]; // ProductSummary & { roles: ('vendor' | 'factory')[] }
  };
}
```

- 每項產品在同一家公司下只出現一次，`roles` 記錄業者、製造廠或兩者，對應規格中「同時擔任兩種角色只列一次」。
- `addresses` 收集該公司在業者地址與製造廠地址中出現過的不重複地址，依出現次數排序，頁首顯示第一個，其餘收合。
- `ProductSummary` 新增 `factoryName`，讓卡片能顯示並連結另一方公司。成分分片也會因此多這個欄位，大小增加有限。
- 估算：全部產品摘要約 11MB（未壓縮），64 片平均約 170KB，gzip 後約 20–30KB；最大的單一公司約 226KB。32 片平均會到 340KB，128 片則大多是很小的檔案，64 片與成分分片一致。
- 收錄所有類別（與成分分片只收一般藥品不同），預設篩選在前端處理，這樣勾選「包含生物製劑」時不用再下載別的檔案。

### D3. 抽出共用的產品清單模組

新增 `src/lib/product-list.ts`，從成分頁搬出並參數化：

- `filterProducts(products, options)`：物種（含水產、蛋雞／蛋鴨）、劑型、產地、效期、類別、角色篩選，回傳結果與被排除的蛋雞／蛋鴨數、被預設條件隱藏的各類數量。水產物種集合改用 `filter-engine.ts` 的同一份定義。
- `groupProducts(products)`：單方／複方 → 劑型大類分組。
- `renderProductCard(product, context)`：回傳卡片 HTML 字串，所有欄位經過 `escapeHtml()`；`context` 決定要不要顯示「複方包含」（成分頁）或角色標記（公司頁）。

兩個頁面只保留各自的頁首、篩選區 DOM 與事件綁定。這些是純函式，可以用 Vitest 直接測試，不需要 DOM。

- 替代方案：公司頁複製一份成分頁的程式。最快，但兩份篩選邏輯很快就會不一致，既有的蛋雞處理已經重複過一次。

### D4. 連結改動範圍

新增 `companyUrl(name)` 到 `src/lib/url.ts`（內部先做 `normalizeCompanyName`）。詳情頁（`render-product.ts`）、比較表（`compare.astro` 的業者與製造廠列）、搜尋結果卡片的業者、成分頁與公司頁卡片的業者與製造廠，名稱不為空白時包成 `<a href="${companyUrl(name)}">`，空白時照舊顯示「未載明」。搜尋結果卡片不是整張可點擊，不會產生巢狀連結。

## Risks / Trade-offs

- [名稱變體沒有合併，同一家公司可能分散在兩個公司頁] → 目前資料正規化後沒有發現業者名稱變體；D1 只合併空白差異。之後如果發現變體，可以在 `data/` 新增公司別名對照表，不影響網址格式。
- [中文名稱的網址很長，貼到通訊軟體時可讀性差] → 可接受；網站已知不做 SEO，也不提供預覽卡。
- [抽出共用模組可能改變成分頁行為] → 先補成分頁篩選與分組的單元測試並確認通過，再搬移程式；手動驗收時比對成分頁改動前後的分組與數量。
- [公司名稱含 `&`、`"`、`<` 等字元] → 網址一律 `encodeURIComponent`，畫面一律 `escapeHtml()`；測試涵蓋含特殊字元的名稱。
- [分片總量多 11MB，GitHub Pages 部署變大] → 使用者只下載需要的分片；`dist/` 從現在的規模增加有限，仍遠低於 Pages 的 1GB 限制。

## Migration Plan

純新增功能，沒有網址或資料格式的破壞性變更。部署後舊的詳情頁、成分頁連結照常可用。若需要回滾，還原 commit 並重新部署即可，公司分片會在下次建置時被清掉。
