## Context

資料來源為農業部開放資料「動物用藥資訊」（id=023，提供單位：動植物防疫檢疫署），每週更新，授權為政府資料開放授權條款。API 端點：

```
https://data.moa.gov.tw/Service/OpenData/FromM/ADProData.aspx?IsTransData=1&UnitId=023
```

欄位：許可證字號、動物用藥品中文名稱、動物用藥品英文名稱、業者名稱、業者地址、製造廠名稱、製造廠地址、劑型、包裝、效能(適應症)、成分、核發日期、有效期間、外銷專用。資料集不含停藥期、用法用量、價格與藥物分類。

目標使用者為獸醫與養殖戶，主要以手機使用，常透過 LINE 分享資訊。

## Goals / Non-Goals

**Goals:**

- 每週自動取得完整資料，資料不完整時不發布。
- 讓使用者依成分找到可替代產品（A），並能並排比較最多 3 項產品（C）。
- 物種使用限制（特別是產蛋中蛋雞／蛋鴨）必須在搜尋、成分頁、比較頁中一致且明顯地呈現。
- 純靜態部署，零伺服器維運成本。

**Non-Goals:**

- 停藥期、用法用量、價格。
- 疫苗依菌株／疾病歸類（生物製劑僅提供文字搜尋與詳情頁）。
- LLM 輔助抽取、濃度結構化比較。
- 會員、收藏、留言等需要後端狀態的功能。
- 用藥建議。本站只呈現許可證資料，不判斷療效或適當性。

## Decisions

### D1. 純靜態網站：Astro，建置時產生所有頁面

資料量小（約 1.4 萬筆）、每週才更新，不需要執行期資料庫。Astro 在建置時產生產品頁、成分頁，搜尋與比較在瀏覽器端執行。

- 替代方案：Next.js 靜態輸出，功能相近，但 Astro 預設零 JS、頁面更輕，適合行動網路。
- 替代方案：有後端的 SQLite FTS。搜尋品質較好，但需要主機與維運，目前規模不划算。

### D2. ETL 用 Node.js／TypeScript，與網站共用型別

資料模型型別（`Product`、`Ingredient`、`SpeciesIndication`）由 ETL 與 Astro 共用，同一套工具鏈與測試框架。

- 替代方案：Python。字串處理同樣方便，但要維護兩套環境與重複的型別定義。

### D3. 管線分三段，中間產物落地

```
fetch ──► data/raw.json（不進 git）
            │
normalize ──► data/products.json、data/ingredients.json、data/meta.json（不進 git，建置時產生）
            │
astro build ──► dist/（頁面 + search-index.json）
```

每段可獨立執行與測試；normalize 可以用本機保存的 raw.json 反覆調整規則，不必每次打 API。

原始快照不提交到 git（每週約 12MB，一年會使 repo 膨脹數百 MB）。筆數防呆需要的「上次成功筆數」寫在已提交的 `data/baseline.json`，由部署成功後的流程更新。

### D4. 筆數防呆

fetch 以 `$top=5000` 分頁直到回傳空陣列。以下任一情況視為失敗、流程中止、保留目前線上版本：

- 任一頁請求失敗（重試 3 次後）。
- 總筆數剛好等於 9,999（疑似分頁參數未生效而被截斷）。
- 總筆數比 `baseline.json` 少 5% 以上。
- 必要欄位（許可證字號、中文名稱）缺失比例超過 1%。
- 任一筆資料缺少預期的 14 個欄位名稱（來源格式變更）。

### D5. 產品識別與網址 slug

許可證字號格式為「動物藥製字第09469號」／「動物藥入字第07606號」，號碼可能含英文字母（如 F0106）。slug 規則：`製` → `m`、`入` → `i`，加上號碼，例如 `/drug/m-09469`、`/drug/i-07606`。許可證字號空白或無法解析的資料列略過並記入建置日誌。重複的字號保留最後一筆並記入日誌。

### D6. 產品分類與預設排除

依劑型把產品分為 `general`（一般藥品）、`biologic`（劑型含「生物製劑」）、`raw-material`（劑型含「原料藥」）。另有 `exportOnly` 旗標。

搜尋與成分頁預設只顯示 `general` 且非外銷專用的產品。使用者可以用篩選開關納入其他類別。產品詳情頁一律可以存取。

### D7. 許可證狀態

- 有效期間含「(已失效)」→ `expired`。
- 有效期間可解析為日期且早於建置日 → `expired`（來源尚未標記也視為失效）。
- 有效期間可解析且未過期 → `active`。
- 有效期間空白或無法解析 → `unknown`。

預設篩選為「排除已失效」，`unknown` 會顯示並加上「效期未載明」標記。這樣不會把可能有效的產品藏起來，同時讓使用者知道需要自行查證。

民國年轉西元：年 + 1911。核發日期也有「中華民國1100913」這種無分隔格式，同樣要解析。

### D8. 成分抽取：規則 + 人工同義詞表

1. 清理：`<br>`、`<div>` 換成分隔符，移除其他標籤，解 HTML entity，轉大寫。
2. 切分：以 `;`、`；`、換行、以及接英文的 `、` 切段。
3. 每段去除劑量（數字 + 單位及其後內容）、括號內容、`EACH ML CONTAINS`／`每瓶含有` 等前綴。
4. 去鹽類後綴（HCL、SULFATE、TRIHYDRATE、HYCLATE…）得到基底名稱。
5. 查 `synonyms.json`（人工維護，涵蓋前 200 大成分）得到標準名稱與中文名；查不到的保留基底名稱，標記 `verified: false`。
6. 產品保留清理後的成分原文（`ingredientsText`），供詳情頁與比較頁顯示，因為劑量與濃度不做結構化。

只有一個標準成分的產品視為單方，兩個以上視為複方。生物製劑不做成分抽取（成分是菌株與效價，無法以同一套規則比較）。

- 替代方案：LLM 抽取。覆蓋率較高，但需要 API 金鑰、成本與人工審核流程，列為後續。

同義詞表的建立方式：先跑一次抽取，輸出依產品數排序的基底名稱清單，人工整理前 200 名（合併 AMOXYCILLIN／AMOXICILLIN 這類拼法差異，填中文名）。

### D9. 物種與使用限制的資料模型

適應症原文例如「豬：治療…。雞（不含產蛋中之蛋雞）：治療…。」會解析成：

```ts
type SpeciesIndication = {
  species: SpeciesId;        // 標準物種，如 'pig' | 'chicken' | 'duck' | 'eel-order' …
  label: string;             // 原文物種字樣，如「雞（不含產蛋中之蛋雞）」
  restrictions: Restriction[]; // 如 'not-laying-hens' | 'not-laying-ducks'
  generic: boolean;          // 原文為泛稱（家畜、家禽）時為 true
  indication: string;        // 該段適應症原文
};
```

- 以「物種字樣 + 全形或半形冒號」切段。一段內有多個物種（「牛、馬、豬：…」）時展開為多筆。
- `species-map.json`（人工維護）把原文字樣對應到標準物種，並列出泛稱的成員（家禽 → 雞、鴨、鵝、火雞…；家畜 → 豬、牛、羊、馬）。水產以「目」保存（鰻形目、鱸形目…），並歸入「水產」群組以供篩選。
- 限制以規則偵測：`不含.{0,6}產蛋`、`不含蛋雞`、`不含蛋鴨`、`不含產蛋中之蛋禽` 等。
- 找不到「物種：」結構但全文出現物種關鍵字時，記一筆不含適應症切段的物種（`indication` 為全文），並在建置日誌中統計。

**蛋雞／蛋鴨的篩選行為**：使用者選「蛋雞」時，帶有 `not-laying-hens` 限制的產品預設排除，並顯示「另有 N 項產品不適用於產蛋中蛋雞」與展開開關；展開後的項目要有明顯警示。選「雞」時全部顯示，但有限制的產品必須在列表上顯示限制標籤。

### D10. 搜尋：MiniSearch + 中文 bigram

中文沒有空格，一般斷詞效果差。自訂 tokenizer：英數字以空白與標點切詞；中日韓字元產生單字與相鄰雙字（bigram）。查詢字串使用同樣的 tokenizer，多個 token 以 AND 結合。

索引欄位與權重：中文品名 > 成分標準名／中文名 > 英文品名 > 許可證字號 > 業者 > 適應症。篩選欄位（物種、劑型大類、單複方、國產／輸入、狀態、分類）以 `storeFields` 保存，在客戶端過濾。

索引包含全部產品（含失效），這樣「排除已失效」可以在客戶端切換。效能預算：索引 gzip 後不超過 1.5 MB，在第一次聚焦搜尋框時才載入。超過預算時，依序改為：把適應症移出索引，再把失效產品拆成另一份延遲載入的索引。

- 替代方案：Pagefind。對靜態站很方便，但篩選邏輯（蛋雞限制、預設排除）要做成 Pagefind 的 filter，客製彈性較低。

### D11. 劑型分層

原始劑型如「注射劑(乾粉注射劑)」拆成大類「注射劑」與子類「乾粉注射劑」。沒有括號的（如「注射液」）用 `dosage-form-map.json` 對應到大類（注射液 → 注射劑）。篩選使用大類，詳情頁顯示原文。

### D12. 比較頁

- 網址：`/compare?ids=m-09469,i-07606,m-09451`。頁面靜態產生，由客戶端讀取參數，並從 `products.json` 的精簡版（`compare-data.json`，只含比較需要的欄位）取資料。
- 選取狀態存在 `localStorage`（讀寫都包 try/catch，失敗時退回只用網址），在列表頁以浮動列顯示「比較已選 (n)」。
- 最多 3 項，選第 4 項時提示已達上限。
- 版面：列為屬性、欄為產品，第一欄（屬性名稱）固定；手機上可以水平捲動。物種矩陣列出所有被選產品涉及的物種，儲存格顯示 ✅／—／⚠（含限制，並附限制文字）。
- 成分相同的列要標示出來，差異一目了然；複方要明確標記。

### D13. 部署

GitHub Actions：`schedule`（每週一次，排在來源更新之後）加上 `workflow_dispatch`。步驟：fetch → normalize → test → build → deploy；任一步驟失敗就不部署，並產生 workflow 失敗通知。預設部署到 GitHub Pages（與 Actions 同平台，不需另外申請帳號）。

## Risks / Trade-offs

- [來源 API 格式或欄位名稱改變] → normalize 前先驗證欄位存在與型別，不符就讓流程失敗；線上保留上一版。
- [成分抽取錯誤，把不同成分歸在一起或漏抽] → 詳情頁與比較頁一律顯示成分原文；未經同義詞表驗證的成分頁標示「自動歸類，可能不完整」；建置日誌輸出抽取失敗清單，供維護同義詞表。
- [物種或限制抽取錯誤，導致把蛋雞不可用的藥列出] → 限制偵測的規則要有針對實際樣本的單元測試；只要偵測到「蛋」相關的否定字樣但無法歸類，就保守地當作限制；詳情頁顯示適應症原文。
- [被當作用藥建議] → 每頁顯示免責聲明，比較頁頂部再加一次；不做排名或推薦。
- [客戶端索引太大，行動網路載入慢] → 效能預算與降級順序見 D10；搜尋框聚焦時才載入。
- [同義詞表與物種對照表需要長期人工維護] → 建置日誌列出新出現、未對應的字樣與出現次數，維護者依次數處理。
- [排程時間與來源更新時間錯開，資料晚一週] → 可手動觸發；頁面顯示資料擷取時間，讓使用者知道資料新鮮度。

## Migration Plan

全新專案，沒有遷移。首次上線步驟：

1. 本機執行 fetch 與 normalize，產生同義詞表與物種對照表的候選清單，人工整理。
2. 本機建置，抽查常見成分（Tylosin、Amoxicillin、Florfenicol）與蛋雞限制的樣本。
3. 設定 GitHub Pages 與 Actions，手動觸發一次完整流程。
4. 寫入第一份 `baseline.json`，再啟用每週排程。

回復：部署失敗時線上版本不變；規則錯誤時 revert 對照表或程式碼後手動觸發重建。
